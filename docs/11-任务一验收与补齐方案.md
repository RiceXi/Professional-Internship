# 任务一验收与补齐方案

已确定验收范围：任务一「KV Cache 分页内存管理子系统」。用户已批准按本文阶段顺序推进；完成状态以测试与实验记录为准。

依据任务书第二部分、6.1—6.3 和 8.1：需要块分配与回收、逻辑页表、动态扩页、共享与写时复制、LRU 换出、真实推理验证，以及利用率、碎片、并发容量和长上下文 OOM 对照。仿真器单测覆盖率要求不低于 70%。

## 1. 项目主线

把 KV Cache 看成请求的虚拟内存：序列使用逻辑 token 地址，页表映射到物理块；生成时扩页，分支共享前缀，写入共享页时复制，显存压力下将可换出的页保存到 CPU 并在需要时恢复。

现有持续批处理调度器负责驱动请求，GPU 算子负责完成真实前向。其他任务的公平调度、多租户配额、GPU 虚拟化不列入本次验收。

## 2. 建议架构

建议将页表、引用计数和页状态管理与实际数据搬运分开，使本地仿真与 GPU 验证尽量共享同一套管理逻辑。

- **管理层**：分配、释放、fork、写时复制、驻留状态、LRU 与资源统计。
- **仿真存储后端**：在 CPU 上用可核对的页内容验证复制和换页，支持显式容量约束与确定性负载。
- **GPU 存储后端**：实际保存 KV 张量，执行 GPU 页复制及 GPU/CPU 间搬运。
- **现有引擎适配**：Attention 执行前确保所需页驻留，更新物理 block table，执行期间固定正在使用的页。

当前 `src/data/__init__.py` 会导入依赖 torch 的模块，纯 CPU 管理逻辑的导入边界需要整理。现有 `BlockManager` 可作为复用起点，但其块状态尚不足以表示主机副本、换页中状态与未满共享页。

GPU 路径不能只通过修改页号模拟换页，必须验证实际 KV 数据已经复制完成。异步搬运涉及的页在完成事件之前不能重新分配或参与计算。

## 3. 分阶段实施与验收

| 阶段 | 建议补齐内容 | 可检查的完成标准 |
|---|---|---|
| 一：可在本地验证的分页基础 | 无 CUDA 入口、分配器/页表、动态扩页、连续预分配基线、确定性负载与覆盖率 | 跨页地址正确；释放后资源恢复；分配失败不破坏已有状态；同一负载可重复运行；仿真器单测覆盖率 ≥70% |
| 二：共享与 COW | 序列 fork、共享引用、未满块写入复制、独立释放 | fork 后共享前缀；写入只复制必要页；父子内容互不污染；释放顺序不影响正确性；无泄漏和重复释放 |
| 三：页面置换 | 有容量上限的主机存储、LRU 选择、换出/换入、资源不足处理 | 换入内容与换出前一致；活跃页受保护；共享页映射一致；主机也满时明确报错且状态可恢复 |
| 四：GPU 接入与压力验证 | 连接现有 KV 管理、真实复制和换页、小模型对照、长上下文压力测试 | 页内容往返正确；确定性样本的结果与无换页路径对照；保存峰值显存、并发容量、OOM 与吞吐/延迟数据 |
| 五：交付整理 | 设计图、报告、原始数据、图表脚本、环境启动、答辩和演示 | 从干净环境按命令复现；图表可追溯到原始结果；明确标注仿真与硬件实测 |

建议先实施阶段一，让后续 COW 和换页都有可运行的验证基础。完整 beam search 的搜索算法不是本次重点，但要用并行分支场景证明 fork/COW 正确。

## 4. 最小正确性用例

1. **地址转换**：页首、页尾、跨页与非法地址；物理块离散时逻辑读取仍连续。
2. **动态分配**：空序列、刚好填满、扩展一页、容量不足、释放后再分配。
3. **共享与复制**：完整页和未满页 fork；多个分支分别追加；父序列先释放与子序列先释放。
4. **引用一致性**：引用数等于有效映射数；被引用页不被作为普通空闲页重用。
5. **换页**：写入已知页内容、换出、原物理页被他人复用、再换入核对内容。
6. **压力与失败**：全部候选页被固定、主机空间耗尽、COW 无空闲页；失败不留下半更新的映射。
7. **最终回收**：负载全部完成后，每个块和主机副本都能解释其归属，清空缓存后资源回到初始状态。

## 5. 基线与实验矩阵

建议按机制逐项增加，明确区分以下配置：

| 配置 | 用途 |
|---|---|
| 连续预分配 | 按声明的请求最大长度预留连续空间，作为空间使用基线 |
| 按需分页，无共享、无换页 | 隔离分页和按需分配收益 |
| 按需分页与共享/COW | 观察公共前缀和多分支的额外空间收益 |
| 按需分页、共享与 LRU 换页 | 观察容量扩展及数据搬运代价 |

每组固定模型尺寸、数据精度、物理容量、请求到达顺序、调度规则、长度与随机种子。关闭或固定 CUDA Graph/编译配置，避免混入计算层变化。

负载至少覆盖短长请求混合、高共享前缀、无共享前缀、并发递增、上下文递增和集中释放后再分配。先用可重复生成的合成负载，再选取任务书建议的对话轨迹或长文本补充验证，并记录数据版本与预处理规则。

连续预留与按需分页的对比同时改变分配布局和预留策略，应如实说明；若要进一步区分两者贡献，可以增加连续按需分配对照。

## 6. 指标与报告口径

- **物理容量与占用**：总块数、运行请求引用块数、可复用缓存块数、空闲块数分别记录。
- **有效利用率与内部碎片**：有效物理 token 槽位/已分配槽位，以及未使用槽位的比例；共享数据只计一次。
- **外部碎片**：连续分配的总空闲量与最大连续空闲区；可以报告 `1 - 最大连续空闲区 / 总空闲量`，同时保留分配失败记录，约定空闲量为零时的处理。
- **并发容量**：固定模型和长度组合下，在规定完成条件内可承载的最大并发。
- **OOM 比例**：固定提交负载中的资源不足失败数/提交请求数，区分仿真容量拒绝、主机耗尽与实际 CUDA OOM。
- **换页代价**：换入/换出次数、字节数、等待时间、重算量及吞吐/延迟；增加超时/无进展计数，避免把无限等待算作成功。

仿真器逻辑时间与真实 GPU 时间分别报告。任务书要求的是量化提升与对照，没有给定固定提升百分比，不预先承诺实验一定加速。
