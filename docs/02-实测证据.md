# 评测方法与参考记录

## 数据状态

本页保留仓库已有的测量表，便于理解瓶颈和设计复现实验。记录标注环境为 RTX 4090 D、Qwen3-0.6B、PyTorch 2.13、FlashAttention 2.8.3、FlashInfer 0.6.15、Triton 3.7.1、官方 vLLM 0.26.0，日期为 2026-08-17。这些环境信息和数值尚未在本项目中独立核验，当前仓库未随附对应原始输出、环境锁定与提交标识，因此不能据此宣称课程实验已完成或当前实现达到表中性能。

下文的“朴素参考实现”和“记录中的加速路径”是已有测量的对照标签。不同表使用不同基线；尤其 RMSNorm 表中的 `F.rms_norm` 与当前代码采用的 FlashInfer RMSNorm 不同。标签只解释表内机制，不表示可运行的统一端到端基线。

## 当前可用的验证入口

- `python test/run_all.py`：生成、前缀缓存和混合调度等 GPU 正确性检查。
- `python bench/run_all.py`：本项目 Prefill、执行模式、前缀与并发性能；会清空 `bench/out/`。
- 单项算子基准与外部引擎对照见 [bench/README.md](../bench/README.md)。部分辅助脚本仍使用旧的引擎标识或外部路径，实际支持范围以脚本为准。

## 课程评测还需补齐

应为选定任务定义基线，并保存环境、模型配置、代码提交、随机种子、负载、预热次数、计时边界及原始数据。分页实验需要连续预分配对照、利用率、内部/外部碎片、共享节省与 OOM 数据；调度实验需要到达流、静态批处理对照、请求吞吐、TTFT P50/P99、公平性与饥饿比例。

GPU 算子使用 CUDA Event 记录设备时间，端到端实验记录明确起止点的 wall-clock 时间。冷启动与稳态分开，重复运行并报告离散程度。仿真时间与 GPU 实测时间分别报告；模拟器产生的数据不能写成硬件测量结果。

以下为待复现的已有记录，表内结论仅适用于其声称的测量条件。

## 1. 算子层

在进行端到端的验证之前，我们系统性的把所有算子基本都进行了替换，换成了高性能版本。

> [!NOTE]
> 这里有小伙伴会问到，为什么我们不都是自己手写triton或者手撕xx算子呢？在实际开发中，对于通用算子来说，调库已经是比较高效的了，而只有对于某些特殊需求或者特殊场景下，我们才需要单独优化。

这里我们把每个瓶颈都单独测试，输入形状按 Qwen3-0.6B 的实际维度来（hidden=1024，intermediate=3072，16 头 / 8 KV 头，head_dim=128）。

已有记录中的算子对照如下：


| 算子         | 瓶颈  | 朴素参考实现实现                         | 记录中的加速路径实现                     | prefill 加速 | decode 加速 |
| ---------- | --- | ----------------------------- | ------------------------- | ---------- | --------- |
| RMSNorm    | D   | pow/mean/rsqrt                | `F.rms_norm` 融合核          | 6.4x       | 6.1x      |
| RoPE       | D   | index_select + chunk + rotate | FlashInfer `apply_rope`   | 7.3x       | 7.3x      |
| SiLU+Mul   | D   | `F.silu` + `mul`              | FlashInfer `silu_and_mul` | 6.1x       | 1.6x      |
| MLP        | D   | gate/up 双 GEMM + cat          | 融合 `gate_up_proj`         | 1.2x       | 1.5x      |
| KV 写入      | C   | `index_copy_` scatter         | Triton `store_kvcache`    | 1.5x       | 1.5x      |
| decode 注意力 | A   | 逐条 gather + SDPA              | `flash_attn_with_kvcache` | 不适用        | 3.3~23.6x |




### RMSNorm

朴素参考实现把 RMSNorm 拆成七步：转精度、平方、求均值、开方、归一化、乘权重、转回精度，每一步的中间结果都写回显存。记录中的加速路径直接用 PyTorch 原生的 `F.rms_norm` 融合核，一次读入、在寄存器里算完、一次写回，省掉了中间张量的来回搬运。


| 形状          | 朴素参考实现 (ms) | 记录中的加速路径 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×1024 | 0.070   | 0.011   | 6.35x |
| 8×256×1024  | 0.071   | 0.011   | 6.42x |
| 32×1×1024   | 0.065   | 0.011   | 6.06x |


prefill 和 decode 形状下收益都稳定在 6 倍左右，因为这个算子本身就是带宽受限，融合省的就是显存读写。

### RoPE

朴素参考实现的 RoPE 需要 `index_select` 从缓存里逐 token 取 cos/sin，再 chunk、做四次 elementwise、最后 cat。记录中的加速路径换成 FlashInfer 的 `apply_rope_with_cos_sin_cache`，一个 kernel 全搞定。


| 形状          | 朴素参考实现 (ms) | 记录中的加速路径 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 4096×16×128 | 0.201   | 0.028   | 7.31x |
| 256×16×128  | 0.199   | 0.027   | 7.26x |
| 32×16×128   | 0.200   | 0.028   | 7.25x |


这个加速比不小，主要吃掉了 `index_select` 从 [32768, 128] 缓存逐 token gather 的开销。

### SiLU+Mul

朴素参考实现是 `F.silu` 和 `mul` 两个 kernel，记录中的加速路径用 FlashInfer 的 `silu_and_mul` 单核完成。


| 形状          | 朴素参考实现 (ms) | 记录中的加速路径 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×6144 | 0.112   | 0.018   | 6.14x |
| 8×256×6144  | 0.027   | 0.012   | 2.16x |
| 32×1×6144   | 0.020   | 0.012   | 1.60x |


prefill 长序列 token 多，收益最高（6.14x）；decode 单 token 时 kernel 启动开销占大头，收益收窄到 1.60x。

### MLP

记录中的加速路径把 `gate_proj` 和 `up_proj` 两个 GEMM 合并成一个 `[2*3072, 1024]` 的 GEMM，省了一次 cat 和一次输入读取。


| 形状          | 朴素参考实现 (ms) | 记录中的加速路径 (ms) | 加速比   |
| ----------- | ------- | ------- | ----- |
| 1×4096×1024 | 0.756   | 0.613   | 1.23x |
| 8×256×1024  | 0.343   | 0.302   | 1.14x |
| 32×1×1024   | 0.084   | 0.054   | 1.54x |


GEMM 本身是计算瓶颈，融合的收益只来自少一次 kernel 启动和输入少读一次，所以比 norm/rope 低很多，这是符合预期的。

### KV 写入

朴素参考实现用 `index_copy_`，记录中的加速路径用 Triton 的 `store_kvcache`。这是个纯访存的 scatter，物理上限就是 HBM 带宽，Triton 的收益来自两点：128-bit 向量化访存、K/V 单 kernel 融合，把 `index_copy_` 约 23 us 的固定发射开销吃掉了。


| token 数 (d=1024 bf16) | 朴素参考实现 index_copy_ (us) | 记录中的加速路径 Triton (us) | 加速比   |
| --------------------- | ------------------- | -------------- | ----- |
| 1                     | 23.35               | 15.18          | 1.54x |
| 256                   | 23.26               | 15.01          | 1.55x |
| 4096                  | 23.34               | 14.94          | 1.56x |
| 8192                  | 44.54               | 22.29          | 2.00x |




### decode 注意力

这是记录中的加速路径最大的一处单点收益。朴素参考实现的 decode 是逐条把分页 KV gather 成连续张量，再喂给 SDPA，时间随 batch 线性放大；记录中的加速路径的 `flash_attn_with_kvcache` 直接消费分页 block_table，一个 kernel 处理整批（`bench_decode_attention.py`，B=8，NHEADS_Q=16，NKV=8，head_dim=128）。


| ctx 长度 L | 朴素参考实现 decode (us) | 记录中的加速路径 decode (us) | 加速比    |
| -------- | -------------- | -------------- | ------ |
| 256      | 578.2          | 25.5           | 22.64x |
| 1024     | 575.0          | 31.6           | 18.17x |
| 2048     | 583.4          | 51.6           | 11.32x |
| 4096     | 598.3          | 154.3          | 3.88x  |
| 8192     | 975.2          | 296.5          | 3.29x  |


用 `torch.profiler`（L=2048，B=8，单层）看一下差距到底在哪：


| 引擎  | kernel 数 | 总 GPU 时间 | 关键内核                                |
| --- | -------- | -------- | ----------------------------------- |
| 朴素参考实现  | 1650     | 15394 us | gather(高级索引) 9211 us + SDPA 4459 us |
| 记录中的加速路径  | 100      | 2684 us  | SDPA flash kernel 2551 us           |


朴素参考实现那 800 次 `gather` 就是把分页 KV 逐条搬进连续张量，纯搬运就花了 9.2 ms，SDPA 本身才 4.4 ms。记录中的加速路径把这些 gather 全去掉了，kernel 数从 1650 降到 100。这也解释了为什么 decode 的并发扩展性上朴素参考实现和记录中的加速路径完全是两个量级。

## 2. 机制层：torch.compile 对 prefill 的加速

decode 的形状固定，可以整步录成 CUDA Graph 重放；prefill 的序列长度一直在变，录不了固定形状的图。记录中的加速路径的做法是把 attention / silu / rope 注册成 opaque custom op，让整个 prefill 前向能被 `torch.compile` 编译成一个完整的图（fullgraph，Graph Count == 1）。单请求 TTFT 实测（`bench_prefill.py`，greedy，两边都开 decode CG，只隔离 compile 这一项）：


| prompt 长度 | eager (ms) | compile (ms) | 加速比   |
| --------- | ---------- | ------------ | ----- |
| 32        | 16.47      | 2.77         | 5.94x |
| 128       | 16.23      | 3.20         | 5.08x |
| 512       | 15.97      | 6.40         | 2.49x |
| 1024      | 15.79      | 12.00        | 1.32x |
| 2048      | 22.94      | 22.25        | 1.03x |


短 prompt 的收益最大（发射开销主导，5~6x），长 prompt 收敛到 1.0x（GEMM 计算主导，到了 GPU 算力的物理边界）。编译发生在引擎初始化阶段（冷缓存约 25s，热缓存约 10s），启动期预热一次就摊掉了，稳态推理不再背这个成本。

## 3. 端到端



### greedy 下的 decode 吞吐

以下记录采用 greedy（temperature=0），用于比较两条执行路径（`bench_decode_e2e.py`，prompt=256，max_tokens=128）：


| batch | 朴素参考实现 eager decode (tok/s) | 记录中的加速路径 cudagraph decode (tok/s) | 加速比    |
| ----- | ----------------------- | --------------------------- | ------ |
| 1     | 36.5                    | 429.2                       | 11.76x |
| 2     | 62.1                    | 683.5                       | 11.01x |
| 4     | 98.5                    | 1367.7                      | 13.89x |
| 8     | 141.2                   | 2574.0                      | 18.23x |


单请求 TTFT：朴素参考实现 24.66 ms，记录中的加速路径 16.26 ms。注意朴素参考实现的吞吐从 batch=1 到 8 只涨了 3.9 倍，而记录中的加速路径涨了 18.2 倍，接近线性。差距就来自前面说的 FlashAttention batch decode，以及 CUDA Graph 消除了逐 kernel 发射的 CPU 串行化瓶颈。

### 四引擎连续批处理吞吐（T=0.6）

nano-vllm 直接禁止 greedy，所以四引擎统一用 temperature=0.6 + ignore_eos 来比（`bench_compare.py`，16 条变长请求，prompt 100~400，总输出 1685 token）：


| 引擎                      | wall (s) | 输出 token  | 吞吐 (tok/s) | 相对朴素参考实现  |
| ----------------------- | -------- | --------- | ---------- | ------ |
| 朴素参考实现（eager）               | 10.85    | 1685/1685 | 155.3      | 1.00x  |
| 记录中的加速路径（decode CG + compile） | 0.57     | 1685/1685 | 2957.5     | 19.04x |
| nano-vllm（CUDA Graph）   | 0.74     | 1685/1685 | 2263.1     | 14.57x |
| 官方 vLLM 0.26.0          | 0.52     | 1685/1685 | 3262.2     | 21.01x |


记录中的加速路径相对朴素参考实现是 19 倍，相对 nano 快 1.31 倍，达到官方 vLLM 的 90.7%。这个数据在 greedy 和采样两种场景下趋势一致，说明核心收益（FlashAttention batch decode + CUDA Graph）是稳定的。

这里顺手说一个踩过的坑：采样器里 `_gumbel_sample` 一开始加了 `@torch.compile`，结果连续批处理中 decode 的 batch 会随请求陆续完成而动态递减（16 到 13 再到 8），每个新 batch 都触发一次重编译，编译开销直接算进了稳态吞吐，T>0 场景吞吐掉到 1001 tok/s。去掉装饰器、改回 eager 标准算子（和 ullm / 官方 vLLM 一致）后，吞吐回到 2957.5 tok/s。细节在 [09-Sampler](./09-Sampler.md) 的优化 3。
